# 路线图（Roadmap）

> 里程碑不是「做完了这些功能」，而是「**验证了一个假设**」。
> 每个阶段都写出口条件，达不到就不进入下一阶段。

---

## 一、总览

| 阶段 | 周期 | 核心假设 | 出口条件 |
|---|---:|---|---|
| **M0** | 1 周 | 热键能唤起壳，跑通一个插件 | 按 `Ctrl+Alt+S` → 搜「json」→ 出格式化结果 → 可复制 |
| **M1** | 2 周 | 上下文模型成立，三条闭环能走通 | 剪贴板 / JSON / OCR 三个插件都能用，且 OCR 不撑爆内存 |
| **M2** | 2 周 | 图片链路成立，产品起源闭环 | 拖入图片 → 描摹 → 预览 → 导出 SVG |
| **M3** | 1 周 | 集合效应成立，加插件不改宿主 | 新增 3 个插件，`Sparrow.App` 零改动 |
| **M4** | 1 周 | AI 是可插拔增强而非前提 | 不配 AI 全功能可用；配了 AI 多出翻译入口 |
| **M5** | 1 周 | 能交付给别人用 | 安装 → 首次导出 < 3 分钟 |

## 二、M0：壳能站住

**目标**：一个能唤起、能搜索、能执行、能复制的壳，以及一条完整的插件链路。

### 交付

```text
Sparrow.slnx + 4 个宿主项目 + 1 个插件项目（Json.Format）
Sdk：ITool / IToolHost / ToolDescriptor / ToolContext / ToolResult / Payloads
Core：HistoryEntry / AppSettings / Ports
App：单实例、托盘、全局热键、命令面板（搜索 + 执行 + 结果卡片）
App/Plugins：PluginScanner（只读清单）+ PluginLoadContext（ALC）+ PluginLoader + ToolRegistry
plugins：Json.Format —— 唯一插件，用来验证「加工具不改宿主」这条边界
Settings：JSON 读写（含 schemaVersion + disabledPlugins）
日志：Serilog 滚动文件
模板：dotnet new sparrow-tool
```

M0 只做 1 个插件是有意的：**先把插件链路跑通，再加第二个。** 如果 M0 就上 3 个插件，出问题时无法区分是「契约设计错」还是「某个插件写错」。

### 实际落地（最小壳版）

M0 按「先证明链路，再补基础设施」的方式落地，与上面的完整清单有偏差：

| 项 | 状态 |
|---|---|
| `Sparrow.Plugin.Sdk` 契约 | ✅ 完成 |
| `plugins/Json.Format` 插件 | ✅ 完成 |
| `Sparrow.App`：单实例、托盘、全局热键、命令面板 | ✅ 完成 |
| 内存 `ToolRegistry`（硬编码 `new JsonFormatTool()`） | ✅ 完成 |
| `Win32Clipboard`（读写系统剪贴板） | ✅ 完成 |
| 崩溃日志（`%TEMP%\sparrow-crash.log`） | ✅ 完成 |
| `PluginScanner` + `PluginLoadContext`(ALC) + `PluginLoader` | ⬜ 推迟到 M1 |
| `Sparrow.Core`、Settings、Serilog、`dotnet new` 模板 | ⬜ 推迟到 M1 |

推迟的理由：M0 要验证的是「契约是否好用、壳能否跑通」，不是「加载器是否健壮」。
插件仍然只依赖 SDK——**插件边界由依赖关系定义，不是由「从哪个目录加载」定义**，
所以 M1 换成目录扫描时，插件代码一行不用改。

### 出口条件

| # | 条件 | 怎么验 |
|---|---|---|
| 1 | 冷启动 < 2.5s | 秒表，连测 5 次取中位 |
| 2 | 热键二次唤起 < 150ms | 从按键到面板可见 |
| 3 | 搜「json」50ms 内出结果 | 输入 3 个字符后首项可见 |
| 4 | 格式化结果可复制，剪贴板内容正确 | 已自动化（`PaletteViewModelTests`） |
| 5 | 单实例：双开只出现一个托盘图标 | 手工 |
| 6 | 热键被占用时有明确提示 | 已实现：托盘提示 + 崩溃日志 |
| 7 | 工具抛异常不崩壳 | 已实现：`ExecuteAsync` 外层兜底 |
| 8 | **删掉 `plugins/` 下任一插件目录，宿主仍正常启动** | M0 不适用（编译期引用），M1 验 |
| 9 | **冷启动不加载任何插件程序集** | M0 不适用（编译期引用），M1 验 |

1–3 是性能项，需要在目标机器上用秒表实测；自动化测试只能保证「逻辑正确」，保证不了「够快」。

### 不做

工作区窗口、历史库、OCR、主题切换、开机自启。

## 三、M1：上下文模型成立

**目标**：证明「六种来源 → 一个 ToolContext」的抽象没漏。

### 交付

```text
ContextBuilder（剪贴板 / 手输 / 截图 / 拖入）
ClipboardMonitor（Windows 事件 + macOS 轮询）
SQLite 历史库（含迁移）
剪贴板历史插件
截图 + OCR（插件 + 独立子进程）
设置页（热键、历史条数、插件启用/禁用列表）
开机自启
```

### 出口条件

| # | 条件 | 怎么验 |
|---|---|---|
| 1 | 剪贴板复制后 500ms 内出现在历史 | 手工 |
| 2 | 历史搜索 < 100ms（1 万条） | 灌测试数据 |
| 3 | 截图圈选 → OCR → 文本可复制 | 手工 |
| 4 | OCR 完成后主进程内存回落（子进程退出） | 任务管理器 |
| 5 | 500MB 视频复制到剪贴板，程序不卡不崩 | 手工 |
| 6 | 三个插件都能从面板唤起并完成 | 手工 |

### 关键风险

- macOS 剪贴板无事件，轮询间隔要在「及时」和「耗电」之间定（建议 400ms）。
- OCR 首次使用要下载组件，必须有进度和失败重试。

## 四、M2：产品起源闭环

**目标**：回到最初的痛点——「看到一张图，拿到可编辑的 SVG」。

### 交付

```text
ImageRef 图床 + LRU
图片插件（convert / resize）
SVG 描摹插件（调色板量化 + 路径拟合）
SVG 预览（Svg.Skia 5.1.1）
SVG 导出（.svg / .png）
文件插件（rename / hash）
工作区窗口
```

### 出口条件

| # | 条件 | 怎么验 |
|---|---|---|
| 1 | 1MP 图片描摹 < 2s | 秒表 |
| 2 | 导出 SVG 能在浏览器 / Figma 正常打开 | 手工 |
| 3 | SVG 里无 script / 事件属性 / 外链 | 用 `SvgSanitizer` 单测断言 |
| 4 | 拖入图片直接进入描摹工具（无需先选工具） | 手工 |
| 5 | 描摹结果可「发送到」图片工具转 PNG | 手工 |

### 硬约束

`Svg.Skia` 必须是 **5.1.1**，`SkiaSharp` 必须是 **3.119.4**。升到 5.2.x 会撞 Avalonia 的 Skia ABI，表现为渲染时崩溃。见 [`architecture.md`](architecture.md#版本钉死)。

## 五、M3：集合效应

**目标**：证明「加插件不改宿主」不是口号。

### 交付

```text
Dev 插件：base64 / url / timestamp / guid / jwt / hash   （6 个独立插件）
Text 插件：transform / replace / extract
JSON 插件：toCode / query
dotnet new sparrow-tool 模板稳定
参数持久化（每个插件记住上次参数）
插件启用/禁用 + 卸载
```

### 出口条件

| # | 条件 | 怎么验 |
|---|---|---|
| 1 | **新增 3 个插件，`Sparrow.App` 目录零改动** | `git diff --stat -- src/Sparrow.App` 应为空 |
| 2 | 工具数 13 个，面板搜索仍 < 50ms | 秒表 |
| 3 | 每个工具都能被「发送到」正确类型的工具 | 手工抽查 |
| 4 | 禁用任一插件后，进程内存下降且面板不再显示 | 任务管理器 |
| 5 | 重复启用/禁用 10 次，无内存增长（ALC 真回收） | 任务管理器 |

**第 1 条是插件化的核心验收项。** 如果新增工具还需要碰 `Sparrow.App`，说明契约有漏——M4 之前必须修，否则插件化只是名义上的。

**目标**：AI 是增强，不是门票。

### 交付

### 出口条件

## 九、什么时候该停下来

出现以下信号，**停止加功能，回去磨闭环**：

```text
1. 你自己一周内没主动用过它
2. 每次用都要想「这个工具在哪个分类」
3. 面板搜索结果第一项经常不是想要的
4. 用完还要手动整理结果（复制/粘贴/改名）
```

第 1 条是致命的。其余三条说明**搜索排序和结果动作做得不够快**——加工具解决不了这个问题。
